# MLXL3 — audit de préparation à la v1

Audit du 6 septembre 2026. Périmètre : moteur Python/Metal, CLI, GUI SwiftUI, MCP, bibliothèque Hugging Face, persistance, mises à jour et packaging.

## Cadre et résultats des vérifications

- Checkout audité : `codex/qwen38-decode`, HEAD `cc28202`, **avec les modifications locales déjà présentes**, notamment kernels/tuning et travaux Qwen/LFM. Ce rapport ne garantit donc pas que le DMG publié contient exactement le code audité.
- Machine : Apple M5, 24 Gio, macOS 26.6.2.
- Suite Python : **363 tests réussis, 2 ignorés**, en 5,53 s. Les deux ignorés dépendent de fixtures Qwen/Ling absentes. Le test d’intégration LFM vérifie l’inventaire/configuration, pas une conversation complète.
- Compilation Swift réussie. Autovérifications `--check-chat-timeline` et `--check-mcp-preferences` réussies. Test du transport CLI réussi : gros stdout, NDJSON, annulation et erreurs. `pip check` sans conflit.
- Sondes supplémentaires isolées : faux moteur NDJSON pilotant le vrai `StudioModel`, fichiers de conversations temporaires, petits modèles/cache MLX et mocks réseau. Elles ont révélé les bugs indiqués « Reproduit » ci-dessous.
- Aucun modèle utilisateur supprimé, aucune conversation réelle altérée, aucun correctif applicatif ni push. Les sondes sont dans `/tmp/mlxl3-v1-audit.SySABN` ; seul ce rapport est ajouté au dépôt.

**Limites :** pas de campagne longue multi-modèles ni multi-Mac, pas de remplacement/installation d’une release, pas de reproduction de l’ancien écran noir. Les risques de concurrence et de saturation sont distingués des défauts effectivement reproduits. Des tests verts ne garantissent pas l’absence de bugs.

Priorités : **P1** à traiter avant une v1 publique fiable ; **P2** robustesse et cohérence ; **P3** finition. « Code » signifie constat direct du chemin d’exécution ; « Risque » signifie scénario plausible non reproduit.

## A. Données et cycle de vie — priorité maximale

### A1 · P1 · Reproduit — historique illisible effacé silencieusement

`ConversationStore.swift:77` utilise `try?` pour lire/décoder et retourne `nil` pour un fichier corrompu ou une version incompatible. `StudioModel` crée alors une conversation vide ; `persistNow()` réécrit le même fichier. Sonde : JSON volontairement cassé → historique vide, puis fichier d’origine écrasé. Les erreurs d’écriture sont également masquées (`StudioModel.swift:488`, `:714`) : disque plein ou accès refusé peuvent donner l’impression que les conversations sont sauvegardées.

À faire : distinguer première ouverture/erreur, conserver le fichier illisible, sauvegarde de secours et erreur visible. Ne pas introduire une nouvelle base de données uniquement pour régler cela.

### A2 · P1 · Reproduit — moteur mort mais interface « prête »

`StudioModel.swift:75` appelle `failActiveTurn` après la sortie du moteur. Celui-ci remet l’état à `ready` tant que `readyInfo` existe (`:668`), même si le processus est mort. Faux moteur : delta puis exit 1 → `engineState.isReady == true`, RAM moteur 0. Le prochain envoi échoue au lieu de proposer un rechargement clair.

### A3 · P1 · Reproduit — supprimer le chat actif laisse une génération fantôme

`deleteConversation` (`StudioModel.swift:357`) retire le message actif sans finaliser le tour. À réception de `complete`, le garde de `:625` retourne avant de réinitialiser les identifiants et l’état. Sonde : supprimer pendant une génération → 0 message, mais `isGenerating == true` après la fin du moteur.

### A4 · P2 · Code / risque — changement de modèle et événements anciens

`loadSelectedModel` (`StudioModel.swift:499`) abandonne les identifiants du tour sans terminer le message. L’import de modèle peut rappeler `refreshModels()` et déclencher ce chemin ; le bouton d’import n’est pas protégé par le même garde de génération que les autres actions. Dans `MLXL3Bridge.swift`, `stop()` termine sans attendre puis `start()` lance immédiatement le remplaçant ; les sorties ne portent pas d’identifiant d’instance de processus. Risques : message resté en streaming, ancien événement appliqué au nouveau moteur, bref chevauchement mémoire. Non reproduits en course réelle.

### A5 · P2 · Code — sélection et moteur réellement chargé peuvent diverger

`refreshModels(autoLoad:false)` (`StudioModel.swift:191`) peut changer la sélection, ou annoncer `idle` si la liste devient vide, sans arrêter/changer le moteur existant. Scénario : registre modifié par le CLI pendant que l’app tourne. La présentation du modèle repose alors sur la sélection, pas uniquement sur l’identité du moteur chargé.

### A6 · P2 · Reproduit — un outil interrompu reste « en cours »

`ChatMessage.fail` (`Domain.swift:274`) ne termine pas les `ToolActivity` en état `running`. La restauration conserve cet état. Sonde : démarrer un outil, échouer, sauvegarder/restaurer → outil toujours `running`.

## B. MCP, contexte et frontières de confiance

### B1 · P1 · Reproduit — un exemple de tool call peut être exécuté

`cli.py:717`, `_parse_tool_calls`, analyse toute la réponse brute : un `<tool_call>` dans le thinking ou dans un exemple de code est reconnu comme un véritable appel. Une chaîne d’arguments JSON invalide devient silencieusement `{}`. Risque important avec des outils capables d’écrire ou d’envoyer des données : le texte produit n’est pas une frontière d’exécution suffisamment stricte.

À faire : parsing conscient du format du modèle et des canaux, arguments strictement validés, jamais transformer une erreur de parsing en appel valide par défaut.

### B2 · P1 · Reproduit — Stop n’empêche pas les appels MCP suivants

Dans `_bridge_generate` (`cli.py:1699`), pas de contrôle d’annulation entre les appels successifs. Sonde avec deux appels : le premier active le drapeau d’annulation, **le deuxième s’exécute quand même**. Une requête outil déjà en vol est également synchrone ; le Stop GPU n’annule pas automatiquement son transport.

### B3 · P1 · Reproduit — format natif Gemma 4 non reconnu

Le parseur Gemma 4 installé dans MLX-LM reconnaît `<|tool_call>call:search{query:<|"|>test<|"|>}<tool_call|>`. Notre parseur retourne `[]` sur cet appel valide. La sélection d’un template natif ne garantit donc pas que notre couche MCP sait lire sa sortie. Ne pas confondre « génération texte Gemma compatible » et « MCP Gemma compatible ».

### B4 · P1 · Code — résultats MCP absents du contexte du tour suivant

Pendant un tour, `dialogue` contient les appels et résultats complets. L’événement `complete` (`cli.py:1671`) n’envoie que la réponse finale pour le contexte persistant. Au prochain envoi, `StudioModel.send` (`:372`) reconstruit uniquement les messages utilisateur/assistant, sans réinjecter les activités outils affichées. L’utilisateur voit les sources dans le chat, mais le modèle n’en conserve que ce qu’il a résumé dans sa réponse. Cela nuit également à la réutilisation du préfixe exact.

### B5 · P2 · Code — gros résultats MCP et métriques trompeuses

Le moteur reçoit le résultat intégral, l’UI au plus 4 000 caractères (`cli.py:1716`). Aucun budget de tokens par résultat : une réponse outil volumineuse peut saturer le contexte avant la synthèse. Les stats finales viennent seulement du dernier passage du modèle : le TTFT affiché ne représente pas nécessairement le délai entre le clic utilisateur et la réponse après toute la chaîne MCP.

### B6 · P2 · Risque — limites stdio insuffisantes

Dans `mcp.py`, `_request` renouvelle son attente pour chaque notification : un serveur bavard peut empêcher un véritable timeout global. La file stdout n’a pas de budget explicite de taille, contrairement à certaines protections HTTP. La pagination `tools/list` n’a pas de garde contre un curseur répété. À tester avec serveur lent, notifications infinies et résultat excessif.

### B7 · P2 · Code — « processus local » ne signifie pas « données locales »

Le texte de confidentialité doit être plus précis, y compris dans les ajouts récents. Un serveur MCP stdio est lancé sur ce Mac, mais son subprocess n’est pas isolé du réseau : il peut lui-même appeler un service distant. Les téléchargements, mises à jour et MCP doivent avoir des descriptions séparées ; ne pas promettre qu’un outil stdio ne transmet rien.

## C. Moteur EXL3, kernels et cache

### C1 · P1 · Reproduit — checkpoint incomplet accepté avec poids aléatoires

`checkpoint.py:336` charge les poids ordinaires avec `strict=False`. `strict_modules` ne vérifie que certains chemins EXL3. Sonde : modèle factice contenant un Linear, aucun poids ni module fourni → chargement déclaré réussi, Linear conservant son initialisation aléatoire. Le descripteur absent/incomplet peut aussi produire une liste de modules vide.

À faire : contrôler l’inventaire attendu, en distinguant explicitement les poids remplacés/fusionnés/tied légitimes. Pas simplement basculer tout en `strict=True` sans tenir compte des adaptations.

### C2 · P1 · Reproduit — cache de préfixe corrompu après erreur de prefill

`GenerationSession.prepare` (`cli.py:329`) modifie le cache avant de valider `self.tokens`. Annulation et garde mémoire réinitialisent la session, mais pas une erreur générale au milieu des chunks. Sonde : exception au deuxième chunk → tokens enregistrés `[]`, état cache `[1,2]`. Retenter le même prompt produit `[1,2,1,2,3,4]` au lieu de `[1,2,3,4]`. Le bridge garde le moteur vivant après l’exception, donc cette session peut être réutilisée.

### C3 · P1 · Reproduit — experts MoE K=7 non utilisables au decode

`kernels/qmv.py:1285` lève `NotImplementedError` pour le chemin expert-mapped K=7. Sonde avec petit `EXL3SwitchGLU(bits=7)` : échec effectif. Le support K=7 d’une projection dense n’implique pas celui d’un expert MoE. Il faut au minimum refuser ce checkpoint avant de l’annoncer prêt, ou compléter le chemin.

### C4 · P2 · Code / risque — validation tensorielle inégale

`_load_all_safetensors` fusionne les fichiers `model*.safetensors` avec `weights.update`, sans rejet des clés dupliquées ni vérification globale de complétude des shards. Les validations des entrées packed/dtypes/shapes ne sont pas uniformes entre QMV et QMM. Un checkpoint incompatible doit être rejeté côté Python avant un kernel Metal, pas découvert pendant la génération. Pas de test de lecture GPU hors limites volontairement provoqué.

### C5 · P2 · Code — budget cache non garanti sur toutes les sorties

`GenerationSessionPool.prune` (`cli.py:491`) n’est appelé qu’après un tour réussi (`:1807`), pas après les sorties erreur/annulation. Les sessions inactives peuvent donc rester au-delà du budget après plusieurs tours interrompus. La session active est exemptée de l’éviction : le budget de pool n’est pas un plafond global mémoire du moteur.

### C6 · P2 · Code — chemins CLI et GUI différents

`attention.py:16` désactive par défaut l’optimisation Gemma SDPA512 ; `MLXL3Bridge.swift:175` force `grouped` dans le GUI sans override utilisateur. Les mesures CLI ne représentent donc pas automatiquement le GUI pour ce cas. Il faut tracer le profil réellement activé et tester les mêmes réglages lorsqu’on compare.

### C7 · P2 · Couverture — compatibilité EXL3 trop large pour les garanties disponibles

Le chargeur s’appuie sur les classes upstream, mais les adaptations de noms, projections, experts, caches récurrents et formats d’outils ne sont pas universelles. Certains empilements MoE imposent une quantification/codebook homogène. La détection TensorOps utilise notamment une architecture GPU exacte (`applegpu_g17g`). Aucune conclusion générale sur tous les M5/M1–M4 ne découle du test sur ce M5.

Il manque une matrice : **architecture × checkpoint/quant × texte × cache multi-tour × MCP × appareil**, avec statuts testé/expérimental/non pris en charge. Les tests de kernels existants passent ; cet audit n’a pas découvert d’erreur numérique sur leurs shapes couvertes.

## D. Rendu, longues réponses et expérience de chat

### D1 · P1 · Risque étayé — traitement non borné des très longs blocs de code

`StreamingTextChunker` (`MarkdownResponseView.swift:333`) annonce un hard limit de 16 000 caractères, mais ne coupe pas dans une fence ouverte. Un long HTML en cours de génération reste donc un énorme bloc Markdown. Le parsing repart de son texte ; `CodeTextChunker` (`:515`) repart aussi du code et découpe les longues lignes par recopie de suffixes. Ces rescans/copies peuvent devenir très coûteux quand le texte augmente.

**Cela justifie un test ciblé mais ne prouve pas la cause de l’ancien écran noir.** Il faut mesurer frame time, mémoire UI et temps de parsing sur code de 10k/100k/plusieurs centaines de milliers de caractères, avec arrêt et scroll. Ne pas changer tous les composants de rendu avant cette mesure.

### D2 · P2 · Code / risque — historique coûteux à afficher et sauvegarder

`MessagesView` (`ChatComponents.swift:3`) utilise une pile non virtualisée. La persistance reconstruit et encode toute l’archive lors des sauvegardes planifiées pendant le streaming. Les snapshots conservent plusieurs représentations d’un même texte (contenu, parts, contexte). Plus l’historique grossit, plus ces coûts et doublons grossissent. Une sauvegarde de fond déjà engagée et `persistNow` ne passent pas par une unique séquence d’écriture, autre risque de snapshot final remplacé par un plus ancien.

### D3 · P2 · Code — l’animation token par token n’est pas implémentée

`SmoothTokenText` (`MarkdownResponseView.swift:1130`) retourne simplement `content` ; `source` et `streaming` n’y sont pas utilisés. Il existe de petites animations d’apparition de blocs, mais ce n’est pas le dévoilement fluide des nouveaux tokens demandé. Le thinking utilise également du texte mis à jour par morceaux.

### D4 · P2 · Code / risques — Markdown, code et LaTeX ont encore des bords fragiles

- Fences basées sur le préfixe triple backtick, sans gestion complète des fences plus longues ou `~~~`.
- Gros tableaux : chunking sans état de tableau, donc risque de perdre l’en-tête et l’alignement après une coupure.
- Coloration découpée : état lexical inter-chunks incomplet pour commentaires/chaînes multilignes.
- Parser inline/math simplifié : combinaisons dollars monétaires, code et délimiteurs à couvrir par des fixtures.
- Cache d’images LaTeX sans budget explicite ; rendu d’une nouvelle formule synchrone. Formules nombreuses/énormes à tester.

Ce n’est pas une preuve que tous les tableaux ou formules échouent : ce sont les cas limites non garantis par le parser actuel.

### D5 · P3 · Code — finitions concrètes

- Ctrl+Entrée ajoute un saut de ligne **à la fin** de `draft`, pas nécessairement au curseur (`ChatComponents.swift:443`).
- Le brouillon est global ; changer de conversation ne restaure pas un brouillon propre à chaque chat.
- La recherche de conversations porte sur le titre, pas sur l’ensemble des messages.
- Pas de parcours complet de récupération/export/import de conversations, ni de corbeille/annulation après suppression.
- Les dernières métriques du widget peuvent provenir d’une conversation d’un autre modèle : identité/ancienneté à afficher.
- Accessibilité à terminer : navigation clavier/VoiceOver, alternative textuelle pour les formules, petits libellés/contraste et respect de Réduire les animations. Revue de code, pas validation VoiceOver exhaustive.

## E. Modèles, téléchargements et CLI

### E1 · P1 · Reproduit — progression HTTP bloquée à zéro

`hub.py:228` ne publie les updates tqdm que pour `unit == B` et une description contenant `Reconstruct`. Une barre HTTP classique `Downloading` est ignorée. Sonde : mise à jour de 100 octets → seul événement visible, valeur initiale 0. Le fichier peut donc télécharger sans progression affichée ; cela ne prouve pas un blocage réseau. Il faut tester Xet **et** HTTP, ainsi que l’agrégation multi-fichiers et la reprise.

### E2 · P1 · Code — « installé » ne garantit pas un checkpoint complet

`hub.variants` (`:53`) vérifie surtout configuration/descripteur et présence de poids ; pas l’ensemble attendu des shards/tensors/tokenizer. L’enregistrement local ne remplace pas une validation complète. La promotion du dossier intervient avant l’enregistrement : si l’écriture du registre échoue, on peut garder un dossier installé mais non enregistré, qui bloque la tentative suivante par collision de destination.

### E3 · P2 · Reproduit / risque — registre fragile

`registry.load_registry` (`:58`) lève `AttributeError` sur un JSON valide mais de mauvais type (`[]`, `null`, chaîne), au lieu d’une erreur gérée. `save_registry` (`:74`) utilise un nom temporaire commun et aucune exclusion interprocessus : GUI et CLI concurrents peuvent perdre une modification ou se gêner sur le replace. La liste conserve aussi des entrées dont le dossier a disparu ; il manque une réparation/relocalisation explicite.

### E4 · P2 · Code — CLI et GUI ne téléchargent pas selon le même contrat

Le downloader CLI historique (`cli.py:1826`) utilise un snapshot du dépôt ; le GUI passe par sélection de variante, staging et promotion. Un dépôt multi-quants peut donc coûter beaucoup plus de disque via le CLI. Les règles d’écrasement/reprise/enregistrement ne sont pas unifiées. Réutiliser le chemin robuste commun vaut mieux que maintenir deux téléchargements différents.

### E5 · P3 · Code — bibliothèque à finir

- Recherche HF bornée aux premiers résultats, sans pagination : modèles moins populaires parfois introuvables avec plusieurs termes.
- Détails/branches mis en cache sans vraie politique de rafraîchissement ; dépôt modifié pendant la session potentiellement invisible.
- Reprise sur disque existante, mais pas de liste persistante claire des téléchargements interrompus après relaunch ni de nettoyage explicite de leurs fichiers partiels.
- Dépôts privés/gated : parcours d’authentification orienté token/CLI, pas onboarding intégré réellement « DMG et c’est tout ».
- Pas de prévalidation complète architecture/quant/mémoire avant de lancer un téléchargement lourd.

## F. Updates, distribution et qualité de release

### F1 · P1 · Code — hotfix même version invisible pour l’updater

`UpdateManager.swift:141` exige `latest > current` pour la version sémantique. Republier un DMG corrigé en `0.4.6` ne déclenche pas de mise à jour sur une installation déjà `0.4.6`. C’est directement pertinent pour les hotfixes publiés sans changement de version. Il faut soit augmenter la version, soit comparer un numéro de build/release réellement distribué.

### F2 · P2 · Code / risques — installation bloquante et rollback limité

La préparation de l’installation est appelée depuis le MainActor. `runProcess` (`UpdateManager.swift:439`) attend la fin du processus avant de vider ses pipes : gel possible si une sortie remplit le pipe. Le shell d’installation supprime la copie précédente dès que `ditto` réussit, avant de vérifier le lancement effectif du nouveau moteur/app. Le rollback couvre l’échec de copie, pas une version qui ne démarre pas.

### F3 · P1 pour une diffusion grand public · Code — packaging non finalisé

`scripts/build-macos-app.sh:71` signe ad hoc (`--sign -`) ; le chemin de build inspecté ne comporte pas de signature Developer ID/notarisation. L’updater vérifie signature/intégrité et bundle ID, mais pas une identité éditeur Team ID attendue. Le parcours de confiance/distribution doit être traité avant de présenter la v1 comme une installation grand public sans friction. Aucun contournement de la sécurité macOS n’est recommandé.

L’app reste **macOS Apple Silicon**, avec minimum système déclaré dans le bundle ; ce n’est pas un binaire Windows/Linux ou Intel. « Tout-en-un » concerne l’installation de ses dépendances, pas une compatibilité avec tous les PC.

### F4 · P2 · Code — versions moteur/UI et builds pas assez traçables

CLI editable, moteur embarqué et sources locales peuvent différer. Le packaging utilise l’environnement local, certaines dépendances ont seulement une borne minimale (`pyproject.toml`), sans lock global trouvé. Un commit MLX-LM est fixé, mais pas tout l’environnement. Le smoke test du bundle est `list --json`, pas une inférence Metal complète. Afficher/archiver versions, commit et profil moteur évitera les comparaisons de builds différents.

### F5 · P1 avant promesse de stabilité · Couverture — tests de release incomplets

Pas de workflow CI `.github` trouvé. Les tests existants ne couvrent pas les scénarios ayant échoué dans les sondes de cet audit. Manquent en particulier : crash/relaunch, suppression pendant génération, erreur de sauvegarde, cache après exception, formats MCP natifs, Stop entre outils, téléchargement HTTP/reprise, très longue réponse et installation réelle de mise à jour.

### F6 · P2 · Code — matrice de benchmarks encore insuffisante pour valider une v1

Le benchmark reproductible récent est une bonne base, mais il lui manque le commit/dirty state moteur, versions complètes MLX/MLX-LM, révision/hash du modèle/tokenizer et overrides kernels. Il mesure le flux Python/callback, pas la vitesse de rendu GUI ; son chemin sans session ne couvre pas le cache utilisé dans l’app. Il faut distinguer TTFT bout-en-bout, prefill réellement évalué, decode GPU et débit affiché. Quelques répétitions ne donnent pas un P95 solide, et il manque une validation de qualité des sorties à côté de la vitesse.

## Ordre de travail recommandé — sans lancer les correctifs maintenant

1. **Intégrité et contrôle** : A1–A3, B1–B4, C1–C2. Aucun texte ne doit se perdre, aucun outil partir après annulation, aucun cache faux être réutilisé.
2. **Chargement et installation fiables** : C3–C4, E1–E4, F1–F3. Refuser tôt les cas non supportés, rendre téléchargement et update réellement récupérables.
3. **Longues sessions** : A4–A6, C5, D1–D4. Mesurer avant d’optimiser ; préserver scroll, arrêt, RAM et responsivité sur gros code et gros historique.
4. **Cohérence et finition** : profils CLI/GUI, contexte MCP, métriques, bibliothèque, raccourcis, accessibilité et messages d’erreur FR/EN.
5. **Validation v1** : tests régressifs des bugs reproduits, scénarios end-to-end sur Qwen dense/MoE, LFM et Gemma réellement disponibles, plusieurs tailles de contexte, puis installation depuis un compte/mac propre et au moins un autre GPU Apple Silicon.

La priorité n’est pas d’ajouter un autre moteur, un autre renderer ou une grosse architecture d’abstractions. Le plus gros gain v1 vient de contrats cohérents, erreurs visibles, états correctement terminés et tests qui couvrent les chemins de panne.
