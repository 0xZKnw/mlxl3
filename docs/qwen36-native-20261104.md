# Qwen3.6-35B-A3B — inférence Rust/Metal sans MLX

Portage de l'inférence ordinaire du checkpoint EXL3 local, basé sur
`0xZKnw/mlxl3/main` au commit
`28f1a84e5371775205aeace22f4bf391a301a884`. Le code est dans le clone isolé
`build/native-qwen36-zero-mlx`, branche locale `codex/qwen36-zero-mlx`, avec
modifications locales identifiées par les empreintes et le diff conservés.
La branche Desktop d'origine et ses neuf lignes de journal préexistantes sont
préservées. Ces résultats précèdent la préparation de la PR ; voir la révision d’intégration en fin de rapport. L’application installée reste inchangée.

## Comportement livré localement

Le moteur natif détecte `qwen3_5_moe` dans `run`, `forward`, le bridge Desktop
et le serveur OpenAI. Cette première session est explicitement limitée à la
géométrie du Qwen3.6-35B-A3B installé : 40 couches, largeur 2048, 256 experts,
top-8, GDN 16/32 têtes de largeur 128, attention 16/2 têtes de largeur 256,
vocabulaire 248320. Les poids EXL3 2,49 bpw restent inchangés.

Les projections, groupes EXL3, GDN et experts déjà portés sur main sont
réutilisés. La session assemble normes, attention/RoPE/KV, mélange MoE,
résiduels et tête. Les tokens et limites sont contrôlés avant modification
de l'état ; les erreurs restaurent le snapshot possédé par la session.
Le cache de prompt retient un préfixe complet, avec propriétaire et conversation.
Le sampling, streaming, découpage réflexion/réponse et transport communs sont
conservés. Les champs de capacité annoncent explicitement que MTP et DFlash
Qwen ne sont pas encore portés dans ce backend ; aucune bascule vers MLX.

Le préfill est **sériel**, suivant la trajectoire AR de référence. Le préfill
multi-lignes historique, Qwen dense, vision, quantification et les sessions
spéculatives Qwen ne sont pas qualifiés par ce changement. Le convertisseur
de l'application garde ses dépendances existantes ; ce résultat concerne
l'inférence du moteur, pas toute l'application.

## Défaut numérique trouvé et corrigé

Le premier modèle complet divergeait après la couche 35 malgré les contrôles
de composants. Les diagnostics indépendants ont établi l'égalité des entrées,
logits/probabilités du routeur, scores, routes et sorties brutes gate/up.
L'expert 179 divergeait ensuite sur 41 des 512 valeurs de préparation SwiGLU.

La cause est le choix des fonctions mathématiques FP32 :
`fastMathEnabled(false)` configure arithmétique sûre **et** fonctions précises,
alors que MLX 0.32.2 configure `MathModeSafe` en gardant les fonctions rapides
par défaut. Les propriétés ont aussi été lues sur le système réel :
safe seul `(mode=0, fonctions=0)`, ancien setter false `(0,1)`.
[Contrat Apple](https://developer.apple.com/documentation/metal/mtlcompileoptions/mathmode)
et [implémentation MLX épinglée](https://github.com/ml-explore/mlx/blob/v0.32.2/mlx/backend/metal/device.cpp).

Le shader routé appelle désormais explicitement `fast::exp` pour cette seule
exponentielle, avec les mêmes arrondis, réductions et règles arithmétiques.
Le contre-exemple réel est conservé dans
`native/tests/fixtures/qwen35-glu-counterexample.json` : test du vrai shader
en échec avant correction (41 différences), puis 512 valeurs identiques après.
Les hooks de diagnostic temporaires ont été retirés ; leurs sources et buffers
restent dans les preuves. Aucune tolérance n'a été relâchée.

## Exécution locale

Depuis ce clone :

```sh
build/artifacts/mlxl3-qwen36-direct run \
  "$MODEL" \
  --prompt "Bonjour" --max-tokens 32
```

Ce binaire est local et expérimental, avec préfill sériel. L'app installée et
ses moteurs existants ne sont pas remplacés. Les résultats ci-dessus sont bornés
aux cas explicitement exécutés ; ils ne prouvent ni une qualité universelle,
ni une égalité avec tous les chemins batchés historiques.
