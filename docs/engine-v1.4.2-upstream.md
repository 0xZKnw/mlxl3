## Essai de projection draft EXL3 par blocs

Préenregistrement `OPT-2026-10-07-MTP-EXL3-BLOCK-HEAD` dans [opti.md](../opti.md). Le prototype indépendant réutilise `_qmv_mapped_tile_kernel.metal`, sans modification du shader : seules les tiles des blocs choisis sont projetées. Poids, scales d'entrée et rotations restent ceux de la tête cible résidente. La vérification cible conserve les 248 320 logits ; seuls les candidats MTP utilisent le sous-vocabulaire.

L'artefact expérimental local reprend 512 blocs/65 536 tokens de la [liste primaire EXL3XPU](https://github.com/sybil-solutions/exl3xpu/blob/15ded2f3add148c4db3c900cba7de878238f53bc/models/qwen3.8-27b-exl3-4.00bpw/draft_vocab.json), sans ajustement sur nos prompts. La couverture publiée concerne uniquement le corpus amont. Cette liste ne prouve pas une identité complète des tokenizers Qwen ; aucun poids ni liste amont n'est livré dans cette PR. Allocation supplémentaire des tables MLX : **425 984 octets (0,40625 MiB)**, distincte de l'empreinte totale du processus.

La projection isolée passe 63 comparaisons synthétiques (21 couples K/codebook, 16 128 valeurs) et trois entrées réelles H2048 (196 608 logits), tous finis et bit à bit identiques à la tête complète puis sélection d'IDs. Une mutation de permutation des tiles est détectée ; restauration et nouveau contrôle réussis. Kani valide la garde CPU sur 0..8 blocs symboliques, u32 et vocab i32 complets, unwind 10, aucune assume : 267 obligations réussies, quatre covers, zéro échec. Une obligation interne inatteignable inspectée. La vraie API MLX rencontre un ICE Kani avant obligations : **Metal/FFI/génération non formellement vérifiés**.

Microbenchmark graphe + synchronisation, M5 Air 24 Gio, MLX 0.32.2, batterie 85% en décharge : 8 warmups, 40 échantillons par passage et 16 évaluations par échantillon. ABBA : 3 413,929 → 1 097,619 µs ; BAAB : 3 538,160 → 1 099,805 µs. Temps de cette seule projection −67,85..68,92%, contrôles ≤1,36%. **Ce n'est pas un gain de génération** et ces conditions ne se comparent pas aux campagnes secteur de phase3.

## Résultat en génération : non concluant, prototype retiré

La qualité de l'intégration a passé quatre tests physiques : récursion D1..3 (24 blocs/80 états), cache-only/position suivante, acceptation/refus/repair et rollback T1..8 sur préfixes 1/23/24/129/256. Tokens, hidden, états cible et KV sont exacts ; `Head::forward` conserve tout le vocabulaire. Le vrai bridge passe 43 requêtes : 35 completions, cinq annulations, deux erreurs attendues et un Tune, budgets et préfixe réutilisé ≥256 vérifiés. Le switch dense→MoE→dense passe 36 completions avec les heads managed ; il ne teste pas le head expérimental.

La campagne réelle utilise le même binaire `e54bc08c6c650dff5c0947dea739420818dc3cc765a338dd1b9c8b4a0232d986` : tête stock A contre blocs B, MTP2, FR+code, 128 tokens warmup/128 mesurés, deux répétitions, contexte 4096, cache OFF, pause 2 s, ordre ABBA. Les sorties/hashes sont identiques. La dérive decode entre passages atteint **−19,287% pour A en français et −26,070% pour A/−12,421% pour B sur code**, au-delà du seuil 3%. Les agrégats +8,906% FR/+17,856% code ne démontrent donc pas un gain causal. Batterie en décharge ; température/fréquences non mesurées. Pas de confirmation BAAB ni nouvelle campagne D0/D1/longue, conformément à la demande d'écarter les essais qui dérivent.

**Tous les changements de code et de tests de ce prototype, y compris l'extension temporaire du runner, ont été retirés.** Sept fichiers restaurés byte pour byte au SHA baseline `b389fcce…`. Aucun changement exécutable issu de cette phase n'est livré. Les sources expérimentales, logs et résultats négatifs restent archivés pour éviter de refaire silencieusement l'essai ; aucune promesse de +10% supplémentaire.

Le loader expérimental avait aussi passé son test CPU (metadata stricte, blocs invalides, conflit Q4, fichier absent/invalide, limite 2 MiB). Le runner temporaire avait passé 25 tests et détecté une mutation envoyant la tête candidate aux deux moteurs. Un filtre GPU mal nommé exécutant zéro test a été rejeté par le contrôleur, puis remplacé par les noms réels : cet échec reste conservé. Premiers builds échoués, Kani MLX ICE et tentative CrossHair impossible dans le venv sont conservés ; sélection CLI non formellement vérifiée. Le premier lancement d'un binaire test absent a échoué avant exécution ; son log brut a été écrasé par le lancement corrigé, absence explicitée dans le journal. La clé d'artefact de head invalide bien le head/prompt cache, mais la clé Tune persistée exclut les heads expérimentaux : aucune validation de clé Tune distincte n'est revendiquée.

Après retrait : `cargo fmt --all --check`, build release `mlx,chat` et répétition du bridge stock 43 requêtes réussis. Sources finales exactes au baseline ; les suites complètes et 39 harnais Kani de phase3 restent celles de ce code, sans transformer les essais expérimentaux en preuve de la livraison. La CI du commit publié est inspectée séparément dans la description de PR.

Les preuves et la décision `block-head-decision.json` sont dans [l'archive phase4](measurements/engine-v1.4.2/phase-4-raw.tar.gz), inventoriée dans [son manifeste](measurements/engine-v1.4.2/phase-4-manifest.json), et dans [opti.md](../opti.md). Les [boosts précédemment confirmés](engine-v1.4.2-pipeline.md) gardent leur protocole propre : pipeline stock code +7,16..7,80% (environ 69–70 tok/s), compact code +7,53..9,80% (75–77 tok/s), campagnes précédentes sur secteur. Ces débits ne sont pas ceux de la nouvelle campagne batterie et les gains ne s'additionnent pas.
