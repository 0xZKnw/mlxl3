## B09: fewer dispatches can lose overlap

The branch at moe.rs464/544 calls `encode_ready_cohort_pending`, whose common preparation/QMV code (projection.rs1413–1567) stops after real down-QMV and retains the existing per-cohort partial/SVH views. Only moe.rs594–611 encodes the fused finish/mix, after the final demanded read. The prior branch encoded each ready cohort's down-finishes before committing its command. Thus hot/early-wave finish work that could previously run during later SSD IO moves to the final command. No ready-wave or command count changes are needed for this lost overlap to exist. Whether it is significant depends on actual GPU/IO timing.

The final shader uses20 CTAs×640 threads,7.5KiB explicit threadgroup storage per CTA (`float[10][128]` plus `half[10][128]`). All ten64-thread route groups take the Hadamard/barriers; after the final barrier, only route0's64 threads perform the canonical mix (90% of the640 lanes inactive in that section). This is a concrete occupancy/critical-tail tradeoff versus the separate64-thread finishes and32-thread mix; fewer dispatches alone do not settle it. B08 changes the Hadamard implementation in the same function, so B08+B09 is correctly compared with other B08-bearing compositions.

No new GPU slab/copy was introduced. Prepared/partial buffers, gate/up buffers and preparation dispatches are shared with the old A06 path; B09 suppresses the old51,200-byte A05 contribution slab. ON retains one partial and one SVH Buffer reference per canonical term (same underlying cohort partial, no duplicated storage), collects pending terms and builds a24-buffer binding Vec plus one parameter binding, versus14 buffers plus a parameter in old mix. Additional bounds/device checks and binding Vec growth are real CPU work; savings from removed per-route finish encoders may outweigh them. No allocation/pipeline time was measured here.

## B10: actual quality counters bound the interpretation

The helper is used by central synchronous commands, dispatch, MoE completion and MoE drain. `ProjectionOutput::read` remains a direct wait; this is not a global replacement of every wait in the repository. Correct terminal Error/status checking remains at callers.

Existing QUALITY-01 model evidence has two before/after counter deltas `[already-terminal, finished-during-spin, fallback, polls]`: `[173,0,150,175664]` and `[239,8,178,215379]`. Most *nonterminal* waits in these short qualification transitions eventually block; this supports checking the budget cost if MAIN32 is weak. It does not measure time spent spinning or MAIN32 behavior. Multiplying fallback counts by50µs gives only a configured upper-budget envelope, not saved/lost wall time: the iteration bound, poll cost and earlier completion differ. Reader threads/desktop work may also compete with host polling. No budget tuning is proposed or tested here.

## B11: file-advice scope and per-record overhead

`TensorInfo::source` already calls `metadata()` for its constituent extent, and `ReadService::sources` independently checks the full expert-record extent. B11's `ExpertFiles::source` adds another `metadata()` to obtain `(dev,ino)` even on a cached descriptor hit (readahead.rs45–66). It then uses the dedicated-FD map and `try_clone`; the old path also clones an FD. The first inode adds `File::open`, a fresh-descriptor identity check and `fcntl(F_RDAHEAD,0)`; subsequent records do not repeat those setters. The original checkpoint open description and page-cache policy remain untouched.

Existing quality counters show five configured inodes and hundreds of selected records, so first-open cost should mostly amortize during warmup. Read-ahead suppression only reduces speculative OS work if such work was wasteful for this workload;1.248MB records and page-cache hits may instead give little opportunity, or sequential/coincident reads may benefit from the old behavior. Logical miss/read-byte parity cannot distinguish these possibilities. Keep the extent/identity/error guards; no metadata check removal or FD protocol change is authorized by this review.

If MAIN32 is weak, inspect these concrete tradeoffs before rejecting the implementations. Do not attribute a group result to one member or add component gains; B10+B11 is a grouped arm, and B08+B09 shares the B08 kernel choice. All performance recommendations remain pending root's fresh controls and final compatible-composition result.
