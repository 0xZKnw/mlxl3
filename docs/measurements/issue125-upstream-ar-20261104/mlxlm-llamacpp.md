## Ranked adaptations

### 1. Defer the final MoE completion to its immediate consumer

llama.cpp submits its Metal graph asynchronously, optionally encoding later segments while the first executes. The ordinary return path does not wait for the whole graph. Synchronization and failure state are explicit boundaries. This is concrete scheduling evidence, not evidence that its thread count or whole graph design suits this model. [Graph submission, lines 474–608](https://github.com/ggml-org/llama.cpp/blob/6f1e6543704bc5b080c7a98e7b6f707b31f6ed51/ggml/src/ggml-metal/ggml-metal-context.m#L474-L608), [synchronization, lines 254–288](https://github.com/ggml-org/llama.cpp/blob/6f1e6543704bc5b080c7a98e7b6f707b31f6ed51/ggml/src/ggml-metal/ggml-metal-context.m#L254-L288).

Our code already overlaps hot/shared/W1 work with SSD reads. It already has P13 and L1 joins. The remaining boundary is narrower: final MoE mix is committed in `native/src/gpu/moe.rs:399`, then `MoeOutput::completed` waits on every owned command at lines 50–66 before `gdn.rs:450/461` can invoke the next HC write. L1 defers that HC write into the following GDN consumer, but still receives an already-completed expert result. `Metal::command` at `gpu.rs:714–746` also commits and waits immediately.

The smallest prospective adaptation is an owned pending expert result consumed on the same Metal queue by the existing HC/L1 continuation. Preserve the CPU gate→demand-plan→SSD boundary; enqueue ordering alone does not authorize publishing a frame or recycling expert slots. Keep all command resources, expert/cache leases and output views until the eventual Completed check. Errors, cancellation, rollback, prefix retention and callers needing CPU output still need an explicit completion boundary. Root is independently auditing this candidate; this note supplies upstream support rather than another prototype.

Relevance is highest because 48 such MoE waits occur per row and the actual immediate boundary is observed. Recoverable time remains unknown. This is distinct from the cancelled expert-compute encoder and generic DEC-ONE proposals: no change to expert shader encoding, resource layout or the CPU router is suggested here.

### 2. Avoid the GDN half→float materialization when the existing HC consumer can read half

llama.cpp has a guarded matrix-product/residual fusion that removes an intermediate only when consumer shape, kernel choice and overlap checks permit it. Its particular few-row MMA path is not directly applicable to our EXL3 projection, but its producer/consumer condition is a useful comparison. [Fusion guards, lines 657–711](https://github.com/ggml-org/llama.cpp/blob/6f1e6543704bc5b080c7a98e7b6f707b31f6ed51/ggml/src/ggml-metal/ggml-metal-fusion.cpp#L657-L711).

An actually unnecessary-looking boundary exists locally: `gdn.rs:290–299` obtains `out_half`, allocates a 2,560-element F32 buffer and dispatches `gdn_to_float`; that shader only casts each half to float (`native/shaders/flash_gdn.metal:78–79`). The next HC write already accepts a half branch, including nonzero branch layout offsets (`hc.rs:573–614`). On F32 streams, its existing `hc_write<float>` half-input branch performs the same conversion at consumption and keeps contraction disabled (`native/shaders/flash_hc.metal:85–94`). Real model streams start F32 at `flash.rs:340–353`.

This could avoid **36 cast dispatches and 36 × 10,240 = 368,640 requested F32-buffer bytes per decode row**, plus their writes and consumer reads, without changing projection math or adding a shader. These are source-derived counts, not measured traffic, RAM savings or a speed prediction. Current composite profiles do not isolate cast time. Preserve the half result's owner through the HC completion. Retain the old public/component trace/export behavior and explicit F16-stream fallback: F32 promotion was an important historical contract (`opti.md:689`). Simply changing the public GDN output dtype for every caller would violate that contract.

This is a source-audit hypothesis, not a verified patch. It needs a fresh preregistration and actual half-branch/F32-stream path counters, finite full hidden/logits/84-state oracles, trace/F16 fallback and rollback checks before any timing. If later selected, one fixed-32-token comparison against the accepted current baseline would be its first speed experiment. No such experiment is authorized or started by this research note.

### 3. Longer-term only: liveness assignments for private ephemeral GDN temporaries

llama.cpp reserves graph buffer assignments and reuses them across compatible executions; in-place reuse requires owned storage, matching layout, one remaining child, no live views and no output role. [Ownership/liveness guards, lines 631–687](https://github.com/ggml-org/llama.cpp/blob/6f1e6543704bc5b080c7a98e7b6f707b31f6ed51/ggml/src/ggml-alloc.c#L631-L687), [reuse of reserved assignments, lines 1052–1097](https://github.com/ggml-org/llama.cpp/blob/6f1e6543704bc5b080c7a98e7b6f707b31f6ed51/ggml/src/ggml-alloc.c#L1052-L1097).

Our HC workspace is already implemented; repeating it is excluded. GDN still allocates ephemeral matrices during encode (`gdn.rs:180–181,206–299`) separately from snapshot-owned previous/next frames (`184–205`). A private local scratch assignment for ephemeral values is therefore structurally missing, but a general graph allocator is disproportionate as the next change. Several raw GDN shaders assume zero-offset buffers; putting arbitrary nonzero-offset subviews in an arena would be incorrect unless every binding/address is adapted. Snapshots, published output and recurrent/history frames cannot be treated as dead temporaries. The current exclusive allocation time for this narrower candidate has not been isolated here, so rank below the two concrete boundaries above.

## Upstream ideas already present, unsuitable, or historically non-new

- **MLX-LM decode lookahead:** it schedules the next graph before yielding the current CPU token. Sampling and log probabilities remain in that device graph. [AR generation, lines 414–492](https://github.com/ml-explore/mlx-lm/blob/736ab0d8c1d0edc79c3d798044fe6904e2fa23be/mlx_lm/generate.py#L414-L492). Our SSD-driven CPU gate and CPU token selection prevent a direct whole-token port. Restoring cancelled P04 or allowing extra state advancement after cancellation would be a different, excluded experiment. Host output overlap alone has no measured material cost here.
- **KV capacity growth:** MLX-LM grows KV storage in chunks and writes new keys/values into capacity. [Cache, lines 339–369](https://github.com/ml-explore/mlx-lm/blob/736ab0d8c1d0edc79c3d798044fe6904e2fa23be/mlx_lm/models/cache.py#L339-L369). Our QSA already doubles bounded slabs, appends in place where safe, and forks published snapshots (`flash_support.rs:3269–3283`, `gpu/qsa.rs:448–469`). Thus “add a KV cache/slab” is not a missing optimization. Sparse QSA's large-context path is not exercised by MAIN87 + 32 tokens despite a 4096 capacity.
- **Packed gated-delta update:** MLX-LM uses a specialized packed kernel with explicit shape fallbacks. [Kernel selector, lines 429–495](https://github.com/ml-explore/mlx-lm/blob/736ab0d8c1d0edc79c3d798044fe6904e2fa23be/mlx_lm/models/gated_delta.py#L429-L495). Our native `packed_gdn_grid(48,128)` / `gdn_step_row` already use that family of packed state mapping (`gdn.rs:182–183,253–271`). It is not evidence of a lost port.
- **MoE reduction fusion:** llama.cpp fuses a recognized expert weighted reduction with nonoverlap guards. [Reduction, lines 612–646](https://github.com/ggml-org/llama.cpp/blob/6f1e6543704bc5b080c7a98e7b6f707b31f6ed51/ggml/src/ggml-metal/ggml-metal-fusion.cpp#L612-L646). Our final `moe_mix` already consumes canonical ordered routes/shared/weights in one dispatch (`gpu/moe.rs:374–389`). A claim that this reduction is absent would be wrong.
- **GDN state write-through:** llama.cpp can write its recurrent snapshot directly into a compatible cache destination. [GDN cache guards, lines 230–288](https://github.com/ggml-org/llama.cpp/blob/6f1e6543704bc5b080c7a98e7b6f707b31f6ed51/ggml/src/ggml-metal/ggml-metal-fusion.cpp#L230-L288). Our step already writes directly to `next.recurrent`; extra cache-copy removal is not available by importing this pattern. Mutable reuse of the old frame would break retained snapshots.
- **Combined a/b projection or norm/gate fusion:** MLX-LM exposes a combined `in_proj_ba` and a compiled precision-aware gate. [Qwen GDN, lines 193–196 and 237–296](https://github.com/ml-explore/mlx-lm/blob/736ab0d8c1d0edc79c3d798044fe6904e2fa23be/mlx_lm/models/qwen3_next.py#L193-L296), [activation, lines 14–18](https://github.com/ml-explore/mlx-lm/blob/736ab0d8c1d0edc79c3d798044fe6904e2fa23be/mlx_lm/models/activations.py#L14-L18). Our two a/b calls and separate norm/gate are visible at `gdn.rs:217–230,272–289`; P11 already discussed the first and T17 exposed a real subnormal rounding mismatch in the second family. They are not genuinely new ideas or drop-in ports. They need actual kernel attribution and a new numerical reason before repetition. No ordinary/fast exp, sigmoid or cast substitution is justified.

No upstream source supports enabling L3+L5 by default without local throughput evidence. Generic fusion/allocation mechanisms explain plausible work removal, but not whether that removal is on this model's critical path. The flat final confirmation remains the relevant result, and the latest user instruction requests research only, with no L3/L5 retest.
