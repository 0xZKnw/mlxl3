## One genuinely absent mechanism: bounded residency sets, secondary priority

TensorFold's actual Flash Next host calls `holdResident` unless explicitly disabled: [flashnext_host.zig, line467](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/zig/src/native/flashnext_host.zig#L467). [flashnext_residency.zig, lines6–26](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/zig/src/native/flashnext_residency.zig#L6) enrolls runner/snapshot buffers, creates the set under the admitted load limit and attaches callbacks for later allocation/removal. [resident.zig, lines27–39](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/zig/src/metal/resident.zig#L27) requests residency and attaches the set to the command queue. [replay_run.zig, lines182–204](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/zig/src/families/flashnext/replay_run.zig#L182) pairs later buffer enrollment and removal. This is used by the serving path, not just a microbenchmark.

Our `Metal::new` creates an ordinary queue at `native/src/gpu.rs:615`; central allocation at `gpu.rs:61–80` calls `newBufferWithLength:options:`. No residency-set integration was found in native Rust/FFI, journal or metal-rs0.33 sources. This is a concrete missing OS-resource-management mechanism, distinct from canceled encoder reuse or a generic memory pool.

Apple documents [queue-level residency sets](https://developer.apple.com/documentation/metal/simplifying-gpu-resource-management-with-residency-sets?language=objc) and [addResidencySet](https://developer.apple.com/documentation/metal/mtlcommandqueue/addresidencyset(_:)). Its CPU-overhead comparison is against repeated explicit encoder resource declarations. **We already bind resources directly and do not issue those explicit declarations**, so that comparison does not establish savings here. TensorFold principally describes keeping a served model wired between requests; this could be more relevant to idle/resume latency than our warmed MAIN32 decode.

Smallest future scope, if an actual residency fault/idle-latency opportunity is first identified: enroll only immutable fixed weights in one optional, hardware/OS-capability-checked queue set, bounded by the existing admission budget; no SSD-slot or transient-buffer enrollment initially. Releasing model state must detach/end residency and preserve ledger accounting. Enrolling every new SSD allocation or snapshot without eviction hooks would risk wired-memory growth. Our existing profile does not isolate residency faults or prove this bottleneck, and metal-rs lacks a ready wrapper here. **Rank below the concrete MoE consumer dependency and GDN fusion work; no tok/s prediction.**

## Confirmed small arithmetic boundary: GDN norm → gate

TensorFold's [fn_gdn.metal, lines178–189](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/zig/kernels/metal/decode/fn_gdn.metal#L178) finishes normalization and gating in the same kernel. Its implementation uses BF16 intermediates, `fma` and its own sigmoid: copying it would violate our reference arithmetic.

Our actual native caller still allocates `normed` F32[6144], submits `p.norm`, then allocates `gated` F16[6144] and submits `p.gate` at `native/src/gpu/gdn.rs:272–289`. `native/shaders/flash_gdn.metal:61–68` fixes the reduction and precise inverse; `flash_gdn_epilogue.metal:31–36` explicitly materializes FP32 sigmoid/product boundaries. A native-only fusion preserving those exact operations could remove **36 dispatches and 36 × 24,576B normed temporary allocations per decoded row**, and 1,769,472 logical bytes of normed write/read traffic. These are structural counts, not GPU time or predicted gain; there is no isolated norm/gate timing in the current profile.

This confirms the parent's existing GDN candidate, not a separate fifth recommendation. History matters: Qwen27 norm/SiLU table experiment09 was model-inconclusive; Flash preparation25 was rejected; T17's earlier MLX epilogue had a numerical failure and is not an oracle to weaken. The current native gate already contains the sigmoid/product consumer, so proposing that consumer alone would duplicate existing work. A norm+gate fusion would need its own independent native component/full-state check, retaining the materialized trace path and exact FP32/FP16 boundaries.

## Larger mechanism, not a small port: GPU expert maps and coarse expert kernels

[fsr_storage.zig, lines46–69](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/zig/src/families/flashnext/fsr_storage.zig#L46) allocates nine persistent component slabs, a logical-expert→physical-slot map and strides. [fsr_runtime.zig, lines149–174](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/zig/src/families/flashnext/fsr_runtime.zig#L149) keeps demand authoritative, overlaps forecasts only when cold unleased slots exist, and binds map/strides into expert kernels. [replay_run.zig, lines392–447](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/zig/src/families/flashnext/replay_run.zig#L392) submits coarse gate/up then down work. The special [Gx path](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/zig/src/families/flashnext/gx.zig#L26) additionally groups repeated experts across wider windows and explicitly requires affine4/group32; its repeated-row advantage is not batch-one AR evidence.

Our actual SSD path at `native/src/gpu/moe.rs:307–343` calls `FlashExpert::encode_view` independently for ready experts; `projection.rs:1080–1136` retains separate projection stages and four output buffers. `MappedSwitchGlu` is not already a GPU-wide expert launch: its resident `forward` still loops over IDs at `projection.rs:1414` and has a different fused floating SwiGLU contract. Thus a true GPU-addressed bank plus batched EXL3 expert kernel is absent from this native SSD path, but requires new EXL3 pointer/offset ownership and rounding work; this is not merely canceled one-encoder reuse.

Do not rank a global cache rewrite as a new quick win: POOL04 already tested shared banks/ARC in the older engine, with no established bank-only gain and negative ARC, then removed it. Current direct-to-shared SSD reads, demand leases, generation-checked publication, hot/cold overlap and prediction support already implement much of FSR's ownership/scheduling pattern (`moe.rs:236–275`, `307–374`). FSR's nine discontiguous stored components are also different from our prepacked one-record/expert source. Its [qualification recipe](https://github.com/ashhart/TensorFold/blob/a26fdae91e0b120fc1e2f3cb8fa3e4095b779f1c/docs/recipes/fluid-subgraph-residency.md#L56) explicitly still requires real checkpoint/device receipts before advertising a memory tier. This is a longer-term design reference, not measured support for a large AR boost.

## Result

TensorFold is public and unambiguous. It corroborates native GDN fusion and exposes a real residency-set gap, but provides no verified, immediately portable large single-stream EXL3 speedup. Keep the parent's MoE wait→consumer and internal cast/fusion opportunities ahead of a residency or expert-bank rewrite. No L3/L5 retest or other experiment was launched.
