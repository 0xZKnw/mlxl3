## 1. Bounded PLE read-ahead for the already-known AR token — small candidate, AR adaptation unmeasured

**Implemented primitive:** M4 `model/ple_store.py:234–269` separates row fetch into bounded issue/finish; `model/ple.py:470–499` computes n-gram keys from known token/context, leaves pending rows in a two-entry memo, drains issued reads on issue failure, then `:435–459` consumes them once. [PLE caller and failure handling](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/model/ple.py#L435-L499), [read issue/finish](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/model/ple_store.py#L234-L269).

**Important caller correction:** `_ple_prefetch` supports single-token calls in its documentation (`model/model.py:1051–1060`), but its **only actual call is `verify2:969`, the MTP path**. Solo AR `forward:1127–1136` does not call it. Thus “PLE prefetch is already deployed/attested in upstream AR” would be false. [Actual call](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/model/model.py#L960-L970), [helper](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/model/model.py#L1051-L1060).

**Native gap:** `native/src/gpu/ple.rs:115–127` calls `Ngrams::read` synchronously when that layer runs; `native/src/flash_ngrams.rs:115–161` computes16 compressed row lookups, reads missing82-byte records individually, validates/decodes, then advances previous-token context. Existing16,384-row cache and streamed embeddings already exist. A native adaptation could issue only this known token's missing PLE rows at the beginning of the token and collect at its PLE layer, preserving identical cache policy, row bytes, Half materialization and context advancement. This is separate from A08/router predictions: no predicted expert and no future token is read.

**Limits / gate:** Only16×82bytes maximum per PLE invocation before cache hits; no evidence this costs meaningful release time. For the fresh-process MAIN32 protocol, the first identical warm request visits at most16×(87+31)=1888 keys per PLE layer, below16384 capacity; native reset preserves the row cache. The measured repeated trajectory therefore has no new PLE misses to hide. This is a source deduction, not a new measured counter. Cold/new prompts are a separate possible scope. Early reads can compete with expert I/O and change failure timing: keep pending data request-owned, never advance n-gram/recurrent state on issue, join on reset/error/cancel/rollback, and compare every row plus continuation/logits/CLI. No MTP implementation is needed, but no isolated AR speed attestation exists; this is not an immediate warm-MAIN32 candidate.

## 2. Device cache lookup + generation-checked expert repair + one-layer lookahead — actual AR, large conditional design

**Production path established:** solo `model.forward:1127–1136` selects `_forward_lookahead:868–945` when all layer kernels are eligible. It builds layer i+1 before settling i; on correction it restores/rebuilds the successor, and drains open fetches on exceptions. This is *intra-token speculation*, distinct from drafting a future token. [AR entry, lookahead and rollback](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/model/model.py#L868-L958).

`spec_build:219–253` dispatches router separately, gathers via the device slot table, treats absent slots as zero-weight provisional contributions, and retains the table generation snapshot. `spec_settle_begin:609–653` reads routes, issues demand reads and optionally starts next-layer predicted reads into **reserve slots**. `_correction:655–697` recomputes only missing/moved-generation pairs, remaps their original top-k positions and reruns the full combine; `spec_settle_finish:699–711` repairs a destination that landed elsewhere. [Actual build](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/model/moe/speculative.py#L219-L253), [settle, repair and destination validation](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/model/moe/speculative.py#L609-L711).

**Ordering is part of correctness:** upstream explicitly relies on a single in-order GPU queue, host router synchronization before later rewrites, current-layer hit protection and reserve-only speculative reads (`speculative.py:609–637`). The [device map and snapshot](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/moe/offload_cache/__init__.py#L1082-L1124) diff-publish changed entries and retain per-slot generations. Generation comparison detects stale values; it is not permission to race host writes with GPU reads.

**Reject direct numerical port:** their [combine113–124](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/kernels/router_combine.py#L108-L125) sums ten routes sequentially. Native `native/shaders/flash_moe.metal:41–53` uses eight canonical stripes followed by the last two routes, and canonical EXL3/Half boundaries differ from their affineQ4 grouped kernels. Copying this combine or their kernels changes the numerical contract. Only scheduling/identity ideas are candidates; native must keep its existing per-expert arithmetic and canonical final full sum, not incrementally add missing contributions.

**Dedup / native delta:** native `gpu/moe.rs:289–319` waits for router IDs/scores before reservation and expert encoding. A completed resident map helper exists in `flash_support.rs:1449` under MLX/test/Kani, not this native production path. However the same broad idea was already researched via Sushi; historical all-hot cohorts were only11.6–11.8%, and about86% of eligible transitions missed. Current AR10 deferred HC/GDN already overlaps some work. JitEngine's detailed partial/generation repair and PLE-aware rebuild are new implementation references, not grounds to repeat old blind speculation or cancelled expert-encoder reuse. Upstream's62.6→50.9ms and router24.5→7.9ms concern an older~16tok/s M4 build and a combined redesign, not an isolated portable saving.

**Prerequisites before a trial:** no-write-while-leased slot invariant, explicit successor rollback covering GDN/conv/HC/QSA/PLE/init state, dropped-work error drain, no updates from invalid predicted routes, capacity shrink/refetch/remap/generation-wrap failures, and independent full-state/logit continuation oracle. The current low-hit3GiB domain may make this counterproductive. Reserve; not a recommended immediate large port.

## 3. Cycle-aware expected-next-use eviction — actual AR policy, requires global scope to be distinct

**Exact rule:** `distance(current_layer, expert_layer) + L*(1-p)/p`, with p the expert's route probability estimated by EMA64 of **past observed layer visits**. It knows the fixed layer order, not future routed IDs. M4 lazily scales per-layer EMA, tracks one farthest resident head per layer, and chooses protected-safe victims with deterministic recency/slot ties. [M4 initialization/key](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/moe/offload_cache/victims.py#L76-L185), [selection and pending-reader rejection](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/moe/offload_cache/victims.py#L237-L359).

M2 README's “layer order alone” is an oversimplification of current code: [M2 victims130–207](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m2/src/jitengine_qwen3_8_flash_next_m2/moe/offload_cache/victims.py#L130-L207) also updates EMA and uses the probability tail. [M2 cache default51–62](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m2/src/jitengine_qwen3_8_flash_next_m2/moe/offload_cache/__init__.py#L51-L62) is64. M4 [solo scheduler239–250](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/src/jitengine_qwen3_8_flash_next_m4pro/scheduler/decode.py#L239-L250) arms the rule only around b=1 decode; prefill/batches use their other policy. This is not MRU/SLRU or previous-token exact route reuse.

**What is attested:** M2 documentation reports trace-replay110.3 vs112.6 misses per step at3,561global slots; full-engine SSD misses~95 vs113 after all changes. It does not isolate the policy's tok/s. Upstream [unit tests](https://github.com/skydiscover-ai/jitengine/blob/2c34508d617800ab7448a69e14a6dd551aec156e/engines/qwen3.8-flash-next-m4pro/tests/unit/moe/test_offload_cache_cyc.py#L99-L258) compare scaled EMA to dense EMA, optimized victim order to full sort, and inject a pending-reader victim bug. Inspected, not executed here.

**Native algebra rules out a superficial port:** `flash_support.rs:1295–1310,1378–1489` stores one512-ID cache per layer, halves LFU counts every16reservations, and uses age ties; baseline is48×53slots. Within a layer, distance is identical for every candidate, so maximizing the upstream key is simply minimizing p: another decayed-frequency policy. The distinctive cycle advantage requires competing experts from different layers in a shared pool or dynamic cross-layer quotas. That overlaps historical POOL01/POOL04, not a new cheap local switch. B12 SLRU is also already tried and worse on decode misses. The *new* policy is distinct from ARC/CLOCK, but a same2544-slot route replay with exact initial state and total budget would be a prerequisite before any runtime revival. No replay was run. Reserve only; no gain promised.

## Checked and excluded

- **pack16 lossless scale/bias codec:** real `moe/offload_cache/codec.py` / `checkpoint/build_p16.py`; MLX4-bit bias is an integer multiple of scale, with a checkpoint-specific escape. Upstream reports3,072,000→2,764,800bytes/expert and about3% for already compact disk records. Native EXL3 record is already1,248,012bytes with different trellis/codebook/scale metadata. No identical scale/bias pair exists to replace; this is not a free10% compression port.
- **Stream embedding / lend prefix-cache memory:** native already reads the BF16 embedding row at `gpu/flash.rs:364–375`; benchmark prefix cache is0. Lending absent prefix entries recovers0bytes. A token-row cache may trade RAM for repeated IDs, but upstream's0.37GiB recovery is already obtained natively and not counted again.
- **Router-lookahead reads:** native A08/qualified prefetch already predicts next-gate experts when enabled (`gpu/moe.rs:662–669`); default depth0 is deliberate. JitEngine miss-chain91.4% used is a different large-cache workload, not permission to silently enable ours or add its percent.
- **MTP, paired recurrence, lazy rejected-draft state, draft vocabulary subset:** excluded by user scope. Sequential affineQ4 kernels, HC fusion already local/rejected, AR30 C01–C04 and cancelled P04/expert encoder reuse are not reintroduced as new mechanisms.

**Recommendation:** no upstream headline establishes another native11–12tok/s boost. PLE issue/collect remains a small cold/new-prompt possibility, with no deployed upstream solo-AR attestation and no expected miss-hiding benefit for repeated warm MAIN32. Slot-map+repair is a much larger transaction design with an unfavorable historical hit domain; cycle-aware global eviction first needs an offline opportunity check. These remain conditional source references, not newly authorized trials. No profiling resumption or executable work is authorized by this research note.
