# AR30 runtime research: allocation, submission and readback

Source/web research only under `AR30-RESEARCH-20261105`, local base `2035348319a76bd505ad6991ccdd510345225568`, qualified AR10 defaults ON and all twelve AR20 options OFF. No executable modification, test, replay, compilation, prover, model/profile run or benchmark was performed. The new issue and a per-candidate preregistration are still prerequisites to implementation. This note does not promise 11–12 tok/s.

**First priorities:** a bounded completion-aware cache of internal Private scratch buffers, and an exact GPU greedy epilogue returning one UInt32. They attack separate visible costs and preserve the accepted kernels. The other four implemented upstream mechanisms below are alternatives/reserves with weaker speed evidence. Persistent arenas, buffer caching and heap allocation address different allocator layers, but are not three additive speedups and may belong to one issue axis. The historical shared-encoder idea is excluded from the six new cases.

## Local evidence and history checked first

The accepted final AR20 baseline reached 10.303/10.020 tok/s in two short default/forced samples; those are historical observations, not fresh controls. The intrusive ALL12 profile has 3,598–3,666 `newBuffer` requests per row (mean 3,640.571), 155.62MB requested per row and 14.04–22.18ms measured host time inside allocation calls. The 7 rows are unisolated instrumentation, not release allocation timings or an additive wall-time forecast. Source: [profile summary](../flash-ar20-20261105/profile/summary.json), `native/src/gpu.rs:62–86`.

`buffer()` currently always calls `newBufferWithLength`, returning a bare owned Metal Buffer. `MatrixView` and snapshots own Buffer clones, with no central lease/cache. The default A06 cohort path allocates prepared/partial buffers and per-route gate/up buffers in `projection.rs:1454–1549`; its output/record/state owners have different lifetimes. The older routed scratch change reused two buffers **within one expert command** (10→6 allocations), not across tokens/frames. Its combined pilot had flat decode and a documented new gate/up WAR edge; a new allocator must not erase that history. [Scratch audit](../issue75-native-routed-scratch-adapt-audit-20261104/README.md). The old HC workspace is an 8 MiB scoped HC facility, not a general Private scratch pool.

A11 already reuses quiescent Shared expert-record backings; A12 already splits an isolated single miss. B11 already has independent read-ahead-disabled FDs; B10 already has the50µs spin experiment. B12 SLRU increases decode misses and is not proposed again. B09's final finish/mix moves ready-wave work to the last command; neither its old slab idea nor that scheduling delay is repackaged here. The [runtime cost/lifetime review](../flash-ar20-20261105/runtime-cost-audit/README.md) and [SLRU audit](../flash-ar20-20261105/slru-audit/README.md) were read. The [slotstream closure](../slotstream-20261026/closure-results.json) withdrew its unqualified runtimes on user request; its late-pipeline losses and invalid concurrent-build speed results are not positive evidence. No SharedEvent cold continuation, global cache-policy replay, P04, MTP/DFlash or HC L3–L5 proposal is counted.

## Six implemented mechanisms and native adaptations

### R1 — bounded completed-buffer cache for internal Private scratch (priority 1)

**Actual upstream:** MLX [allocator.cpp108–170/185–211](https://github.com/ml-explore/mlx/blob/c69303b00f5f61860436e832f23fa8c34b96f93a/mlx/backend/metal/allocator.cpp#L108-L211) tries the cache before allocating and recycles frees; [buffer_cache.h30–84](https://github.com/ml-explore/mlx/blob/c69303b00f5f61860436e832f23fa8c34b96f93a/mlx/backend/common/buffer_cache.h#L30-L84) selects a bounded near-size entry and trims its idle LRU. The code and Swift memory documentation attest implementation, not an isolated allocation speedup.

**Native fit:** prepared/partial/gate/up temporaries in the A06 path are newly allocated each row. Start with an explicitly internal Private-scratch lease family. Keep model weights, Shared SSD destinations, returned outputs, recurrent/KV state and snapshot/prefix buffers outside the pool. Record which command buffers use each lease; reuse only after every associated CB is terminal and every typed view/lease owner is gone. Naked Metal Buffer clones make a blanket replacement of `buffer()` unsafe.

**Protocol:** separate available/pending/leased states, generation IDs, exact storage class and checked capacities; bounded idle bytes and pressure trim of *available only*. If a miss/pressure event occurs while the required CB is not yet submitted, use an allocation/failure fallback rather than waiting for that CB and preventing its commit. Preserve error drain and failed-generation cleanup. Hardware Buffer `retainCount` and Rust `Rc==1` are not completion/ownership oracles.

**Required validation after issue/prereg:** exact nonzero full component/model/bridge states; real per-row fresh/reused counts; two in-flight cohorts, retained outputs/snapshots excluded, dropped owners before commit, forced pressure/trim/OOM, cancel/error/reset/shrink, failure recovery and zero-leak budget accounting. Kani can check the actual bounded lease transitions and range arithmetic, not Metal execution.

**Primary failure evidence:** [MLX#3689](https://github.com/ml-explore/mlx/issues/3689) reports cache trimming an in-flight buffer under an unretained-CB setup; [#3142](https://github.com/ml-explore/mlx/issues/3142) records fast-synchronization/retention and allocation-pressure deadlock hazards. They are failure scenarios to guard against, not evidence our retained native buffers currently have those bugs.

### R2 — exact device greedy epilogue, UInt32 readback (priority 2)

**Actual upstream:** TUFF [Argmax.swift3–30](https://github.com/rexmhall09/TUFF/blob/dc790dd91484f266c4e114fdf00818c3db9dfe48/Sources/TUFFEngine/Kernels/Sampling/Argmax.swift#L3-L30), [LogitOutput.swift43–88](https://github.com/rexmhall09/TUFF/blob/dc790dd91484f266c4e114fdf00818c3db9dfe48/Sources/TUFFEngine/Kernels/Sampling/LogitOutput.swift#L43-L88). Real caller [RealForwardRunner.swift3174–3245](https://github.com/rexmhall09/TUFF/blob/dc790dd91484f266c4e114fdf00818c3db9dfe48/Sources/TUFFEngine/Runtime/Inference/RealForwardRunner.swift#L3174-L3245) appends selection to finalCB, commits/waits, then reads one token; [selectHead902–904](https://github.com/rexmhall09/TUFF/blob/dc790dd91484f266c4e114fdf00818c3db9dfe48/Sources/TUFFEngine/Runtime/Inference/RealForwardRunner.swift#L902-L904) controls the eligible head. Its raw-argmax/affine fused head is **not** our numerical oracle.

**Actual native caller chain:** `main.rs::bridge_generate_round` selects via `direct_bridge::select` (main3319; direct_bridge15–40). That calls `FlashNext::log_probs`→`Metal::flash_log_probs` (`flash.rs344–345,613–650`): upload 248,320 Half logits back to GPU, allocate LSE, synchronize, read 2 bytes, then allocate/map 248,320 F32 values on CPU before first-max selection. The logits already came from `FlashNext::forward`→`prefill`→`prefill_inner` (`390–392,563–609`), whose head currently uses `submit_fp16_view(...).read()`. CLI greedy code around main4553 repeats the normalization route. This is an actual missing path, not a benchmark-only API.

**Adaptation:** choose eligibility before **any state advancement**: native Flash AR, greedy `(temperature==0 OR top_k==1) && repetition_penalty==1`, no requested full logits/logprobs, no speculative/draft modes. Preserve the old public Vec-logits APIs/fallback for all other cases. Keep the LM-head device view; append the identical existing Half-LSE computation and a reduction over `Half(logit−HalfLSE)` with the canonical first-index maximum. Return 4-byte UInt32 only after success. A raw maximum over logits is wrong: existing `normalized_greedy_preserves_half_ties...` explicitly shows distinct logits becoming tied after Half normalization. Match finite/error and masked−infinity behavior from `speculative::greedy_log_prob_id`, including NaN/+infinity/all-invalid rows.

**Transaction boundary:** `prefill_inner` snapshots before hidden/head work, restores on any error and advances offset only on success. The new head/LSE/select/wait/readback belongs *inside the same transaction*. A GPU selector error must restore state; do not call forward again to fall back after advancement. Select a tagged head result before prefill and preserve EOS-before-append, token counters, timings, streaming decode, cancel/reset and the final-budget no-extra-forward rule in main3305–3430. One existing final head CB with an epilogue is preferable to a new upload/CPU round trip; do not change the EXL3 head formula in the first trial.

**Required independent oracle:** CPU implementation of the existing Half LSE/round/subtract/first-max contract (not the candidate shader), including rounding-created ties, signed zeros, subnormals, adversarial finite extremes, masks, NaN/+inf/all−inf, wrong/missing extent, and a raw-argmax mutation that must fail. Then full initial 84-state archive/continuation/logits-capable fallback, two-token real CLI + MAIN32 complete golden, actual scalar-path count and measured host readback byte count. No estimated tok/s saving is established.

### R3 — model/frame scratch preallocation from a fixed lifetime plan (conditional)

TUFF declares persistent hidden/query/dense/MoE scratch once in [RealForwardRunner.swift92–232](https://github.com/rexmhall09/TUFF/blob/dc790dd91484f266c4e114fdf00818c3db9dfe48/Sources/TUFFEngine/Runtime/Inference/RealForwardRunner.swift#L92-L232), sizes the widest layer and allocates in [527–619](https://github.com/rexmhall09/TUFF/blob/dc790dd91484f266c4e114fdf00818c3db9dfe48/Sources/TUFFEngine/Runtime/Inference/RealForwardRunner.swift#L527-L619). MNN [MetalBackend.mm209–223](https://github.com/alibaba/MNN/blob/c95758f4cd4cc4891a89833842dbd681109d3303/source/backend/metal/MetalBackend.mm#L209-L223) uses a deferred allocator with planned tensor offsets.

This is a fixed lifetime/layout plan rather than R1's runtime free-buffer cache. Our all12 A06 prepared/partial/gate/up working sets are bounded, but every hot/cold wave still allocates them. A narrow per-frame scratch plan could keep disjoint simultaneously live cohort regions and only reuse transitively dead regions; returned outputs and snapshots stay fresh. The new domain is the real A06/all12 native cohort path, not the old single-expert scratch or HC workspace. Risks: one large tracked backing can introduce false hazards, reuse can add gate/up WAR edges, and persistent per-layer buffers increase residency. Require poison, overlapping retained frames, failure rollback and actual-allocation counters; preserve current commits/cohort readiness. Treat as an alternative to R1 first, not a separate additive boost.

### R4 — small allocation backing from a bounded MTLHeap (reserve)

MLX [allocator.cpp47–77/140–154](https://github.com/ml-explore/mlx/blob/c69303b00f5f61860436e832f23fa8c34b96f93a/mlx/backend/metal/allocator.cpp#L47-L77) constructs a heap, then allocates small new buffers from it with device-allocation fallback. This attacks backing/resource allocation on R1 cache misses, rather than reuse itself. Our allocator always allocates from the device.

Use a bounded heap for internal scratch only; keep ordinary tracked hazards and storage modes. Do not copy MLX's Untracked resource option without its dependency protocol. Check device support, alignment/size bounds, exhaustion/fallback, ownership and active/pool/heap budget accounting. No aliasable overlap, expert-bank layout change or larger-cache substitution. No isolated upstream or local Flash speed evidence found, so this is a reserve after R1 exposes the remaining allocation cost.

### R5 — validated CPU encode replay for stable native segments (reserve)

MNN [MetalReplay.hpp5–31](https://github.com/alibaba/MNN/blob/c95758f4cd4cc4891a89833842dbd681109d3303/source/backend/metal/MetalReplay.hpp#L5-L31) describes caching PSO/buffer/bytes/grid sequences; [MetalReplay.mm166–220](https://github.com/alibaba/MNN/blob/c95758f4cd4cc4891a89833842dbd681109d3303/source/backend/metal/MetalReplay.mm#L166-L220) validates **all** current bindings before any emit, then emits without repeated per-op pipeline/shape logic. [MetalBackend.mm1489–1493](https://github.com/alibaba/MNN/blob/c95758f4cd4cc4891a89833842dbd681109d3303/source/backend/metal/MetalBackend.mm#L1489-L1493) annotates real bindings. This replays CPU API descriptions, not an already committed CB, and is distinct from numeric kernel fusion or one shared encoder.

Native PSOs are cached, but `encode_bound` still constructs each operation/argument loop and encoder repeatedly. A retained, typed description for a stable resident segment could avoid host branch/allocation churn. Never record a raw borrowed Tensor pointer as in an unsafe blind port: the upstream header itself warns about dangling tensors. Bind owned Buffer/views plus generations; validate every binding/shape/offset/feature before first emit, and fall back only before dispatch. Cold records, KV growth, snapshots, shrink and shape changes invalidate the description. High complexity and no isolated performance attestation found: reserve until profiling identifies CPU encoding beyond allocation.

### R6 — scoped encode-thread QoS with exact restoration (exploratory reserve)

MNN [MetalBackend.mm740–767](https://github.com/alibaba/MNN/blob/c95758f4cd4cc4891a89833842dbd681109d3303/source/backend/metal/MetalBackend.mm#L740-L767) conditionally raises the calling encode/commit thread to user-interactive and restores its previous class/priority at end. The reason in source is avoiding efficiency-core scheduling; implementation is explicit, but no isolated speed result was found.

No `pthread_set_qos_class_self_np` policy was found in the native runtime. A narrowly scoped RAII guard around encode/commit could be evaluated after issue/prereg, restoring on success, error, cancellation and unwind; do not modify global process priority, pin cores or starve SSD workers. This is scheduler policy, not another allocator/encoder case. Conditions, CPU contention and current inherited QoS must be measured first; it may do nothing or worsen power/thermal behavior. It is not evidence for a promised large gain.

## Excluded or merged after checking the implementation

- **Parameters:** `gpu.rs1125–1146` already uses `encoder.set_bytes`; no per-dispatch parameter MTLBuffer exists to remove. MNN constant buffers/staging rings are implementation examples, not a missing parameter optimization here.
- **Raw command-buffer pool:** ordinary Metal3 CBs are one-shot; retaining wrappers or reusing command descriptions is different. No claim of safe CB reset/recommit is made.
- **Shared encoder:** MLX [device.cpp436–468/672–679](https://github.com/ml-explore/mlx/blob/c69303b00f5f61860436e832f23fa8c34b96f93a/mlx/backend/metal/device.cpp#L436-L468) keeps a concurrent encoder plus explicit hazard barriers. Strata [mtl_rt.mm952–1063](https://github.com/Niko1221/Strata/blob/c3b3f5035506f3e966f1b4b7b188aeaabae92f1d/metal/src/mtl_rt.mm#L952-L1063) has per-dispatch barrier metadata. Our helper ends a fresh encoder every dispatch. This might warrant a new **cohort** adaptation, but the user's cancelled same-expert encoder/P04 history precludes calling it untouched/new; keep outside the six priorities unless concrete new pipeline evidence justifies it. Do not simply copy concurrent dispatch without dependency tracking.
- **TUFF 64 MB resident mapping split:** its [README](https://github.com/rexmhall09/TUFF/blob/dc790dd91484f266c4e114fdf00818c3db9dfe48/README.md) reports a large dense-only benefit and a catastrophic oversized-model regression corrected by a residency threshold. Our resident projection tensors already have separate buffers (`projection.rs250`), and our expert records are 1.248 MB, not one multi-GiB bound buffer. No equivalent missing fast path is established.
- **SSD:** common worker queues, per-layer/global residency-policy changes, A11 destination reuse, A12 split reads, SLRU and read-ahead have real prior trials. The current sources do not establish a new high-impact read-dedup/coalescing case for our random equal-size demanded records. Do not count reduced logical misses as reduced physical NAND traffic. Preserve all 48×53slots, exact records, ready-wave timing and generation checks.

The six cases attest implementation, not six measured speedups. The first issue should prioritize R1 and R2, with R3 as a carefully separated memory-planning alternative; R4–R6 remain conditional. Only after issue creation should a new baseline profile, smallest coherent prototype, independent quality gates and brief fresh-control MAIN32 screens determine which are useful.
