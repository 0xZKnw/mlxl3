Résultats du profilage réalisé les **27–28 octobre 2026**, avec les vérifications et suites d’essais disponibles au 29 octobre. Objectif : savoir où part le temps avant d’optimiser Qwen3.8 Flash-Next. Cette issue publie les mesures existantes ; **aucun nouveau benchmark n’a été relancé pour la rédiger**.

**Constat principal :** l’attente CPU des routes recouvre presque entièrement du travail GPU. Le poste de soumission MLX contient en revanche environ **12 ms/token de CPU actif pendant que le GPU est inactif**, principalement dans le premier `async_eval` qui soumet aussi les producteurs amont. Le chemin logique des lectures d’experts comporte une queue exposée d’environ **27–31 ms/token**. Sa part physique SSD/NAND reste **non mesurée**.

Il ne s’agit ni d’un gain livré ni de trois budgets additionnables. Les nombres CPU/GPU fins viennent de fenêtres instrumentées, plus lentes que leurs contrôles. Les résultats postérieurs négatifs sont conservés à la fin pour éviter de présenter les pistes initiales comme des boosts disponibles.

Fenêtre courte : 20 pas complets, AR MAIN. **Unités : ms/token.** CPU = thread d’inférence ; les lecteurs I/O sont sur d’autres threads. GPU actif = exécution de commandes du processus moteur, **pas occupation ALU, ni temps arithmétique pur**.

| Enveloppe hôte | Murale | CPU actif | CPU bloqué | CPU runnable/interruption/préemption | GPU moteur actif | GPU sans activité observée, tous processus |
|---|---:|---:|---:|---:|---:|---:|
| Readback routes complet | 40,056 | 0,302 | 39,473 | 0,281 | 39,947 | 0,106 |
| Soumission MLX | 22,033 | 21,912 | 0,010 | 0,110 | 9,710 | 12,195 |
| Bloc lectures experts | 38,108 | 7,387 | 30,147 | 0,574 | 6,685 | 31,055 |

Les colonnes CPU partitionnent la durée de leur groupe. Les axes CPU et GPU sont **simultanés** : ne pas les additionner.

Pour l’ensemble des pas sélectionnés, la durée vaut **113,755 ms/token**, avec 37,690 ms CPU actif, 75,030 ms CPU bloqué et 63,013 ms de commandes GPU moteur actives (63,622 ms tous processus). L’intersection **CPU actif ET GPU inactif** sur tout le decode vaut **22,150 ms/token** : les 12,142 ms ci-dessous en sont le sous-ensemble situé dans les soumissions MLX, pas tout le CPU exposé.

Corroboration exploratoire sur 36 autres pas d’une campagne interrompue après la phase validée (elle n’est pas une seconde campagne complète conforme zéro swap) : durée 103,204 ms/token, GPU moteur actif 57,233 ms/token, CPU actif/GPU inactif total 22,122 ms/token. Les deux fenêtres sont gardées séparées.

### Routes

Dans l’enveloppe de 40,056 ms : attente source C++ 40,002 ms ; copie 0,00565 ms. Le GPU moteur est actif pendant 39,947 ms. L’autre fenêtre donne une attente source de 35,937 ms et une enveloppe de 36,006 ms, dont 35,929 ms d’activité GPU.

**Conclusion :** enlever l’appel d’attente ne supprime pas ses producteurs. Le résidu sans activité GPU observée dans cette enveloppe est d’environ 0,08–0,11 ms/token, sous réserve du calage. Les routes attendent notamment la chaîne de calcul précédente, pas une copie CPU coûteuse.

### Soumissions

96 appels `async_eval` par token, **pas 96 dispatchs GPU**. CPU actif/GPU inactif dans ces soumissions : **12,142 ms/token**, corroboration 11,803 ms.

Environ 1,166 ms de CPU actif se trouve dans les syscalls observés ; environ 20,746 ms hors de ces intervalles. Ce n’est pas une partition exhaustive user/kernel. L’encodage Metal, les allocations, le suivi des ressources et la traversée MLX restent en partie imbriqués.

5 258 `fstat` du thread principal sur les 20 pas ne représentent que **0,113 ms/token**. Les gardes de troncature/bornes de fichiers ne sont donc pas la première cible de performance.

## 6. Quels appels occupent précisément les 12,142 ms ?

Chaque couche effectue deux soumissions dans `SsdMoe::prepare_resident_hot`, aux lignes de la **source archivée** `ssd_moe.rs:560/569` :

| Appel | Appels sur 20 tokens | Temps mural/token | CPU actif ET GPU inactif/token |
|---|---:|---:|---:|
| `slots.indices().async_eval()` | 960 | 18,323 ms | **11,897 ms — 98,0 %** |
| `output.async_eval()`, résultat Hot | 960 | 3,710 ms | **0,245 ms — 2,0 %** |

Chemin : `Array::async_eval` → `mlxl3_array_async_eval` → `mlx::core::async_eval` → `eval_impl(..., true)` → évaluation/encodage des primitives GPU.

Le premier appel soumet les dépendances des indices : **Cold précédent, combinaison/réduction, HC, attention/GDN et routeur**. Il ne mesure pas seulement le petit kernel cache-map. «Async» évite d’attendre la fin GPU ; la préparation et l’encodage CPU sont exécutés avant le retour.

249 points CPU à 1 kHz appartiennent aux fenêtres exposées : 243 dans le premier appel, 6 dans le second. Une seule frame MLX, la plus proche de la feuille, est choisie par pile pour obtenir des catégories exclusives :

| Frame MLX | Points / 249 | Part |
|---|---:|---:|
| `CommandEncoder::maybeInsertBarrier()` | 39 | 15,7 % |
| `CommandEncoder::get_command_encoder()` | 37 | 14,9 % |
| `CommandEncoder::dispatch_threads(...)` | 29 | 11,6 % |
| `gpu::eval(array&)` | 23 | 9,2 % |
| `eval_impl(vector<array>, bool)` | 21 | 8,4 % |
| `CommandEncoder::commit(...)` | 18 | 7,2 % |
| `CommandEncoder::set_input_array(...)` | 10 | 4,0 % |

Toutes fonctions `CommandEncoder` et callbacks réunis : **143/249 points, 57,4 %**. La simple traversée `eval_impl` n’est pas majoritaire. Le [backend MLX v0.32.2](https://github.com/ml-explore/mlx/blob/v0.32.2/mlx/backend/metal/device.cpp) encode barrières, ressources, encodeurs et fences ; on ne peut pas retirer ces dépendances comme une attente inutile.

**Limites :** ces pourcentages sont des statistiques de sampling, pas des ms exactes par fonction. La feuille `__kdebug_trace64` apparaît 48/249 fois : une part du travail peut venir de l’observateur Instruments. Les allocations/libérations recouvrent les catégories MLX ; ne pas additionner leurs pourcentages.

Le filtre initial exigeant «Running à l’instant du sample» donnait zéro point et a été rejeté. Les 757 points du thread dans le decode se trouvent dans un contexte Interrupted ; ils ont un contexte Running immédiatement précédent. Ce rattachement explicite précède le filtre soumission/GPU idle. Aucun dénominateur vide n’a été transformé en résultat.

## 7. Lectures masquées, queue exposée et limite SSD physique

Dans la fenêtre courte :

- 816 lots, **2 619 retours `preadv`**, chacun de 1 248 012 B, concordant avec les jobs natifs ; **3 268 543 428 B logiquement retournés**.
- Union temporelle des lectures : **37,211 ms/token**, bloc complet 38,108 ms/token.
- Activité GPU moteur concomitante au bloc : **6,685 ms/token**.
- Hot non prêt au début puis prêt au retour dans 751 lots ; encore non prêt au retour dans 61 ; déjà prêt aux deux bornes dans 4.
- Par rapport à la dernière activité GPU indépendante avant le retour I/O : 244 lectures finissent avant, 1 876 traversent cette frontière, 499 commencent après.
- Queue après cette frontière : **31,409 ms/token**, dont **30,862 ms d’union de `preadv`**.

Corroboration sur 36 pas : 1 513 lots, 5 244 jobs, 6 544 574 928 B logiques ; union 31,967 ms/token, overlap GPU 5,329 ms/token ; queue exposée **27,215 ms/token**, dont 26,988 ms de `preadv`.

Ce sont des budgets du chemin **service/copie/OS/ordonnancement**, à ordre de queues fixé. Les classes de lectures décrivent une frontière temporelle ; elles ne démontrent pas la criticité causale de chaque octet ni que leur avancement raccourcirait le token de toute la queue.

### Pourquoi on ne les appelle pas «31 ms de SSD»

`DiskIoRoutines` exporte zéro événement bloc dans la capture modèle. Trois contrôles ont évité de confondre absence de données et absence d’I/O :

1. Témoin jetable 128 Mio écrits + 128 Mio lus, `F_NOCACHE` / `F_FULLFSYNC`, égalité byte-exact ; ses 4 `pwrite` / 4 `pread` et contrôles sont bien visibles, mais zéro événement bloc.
2. System Trace + DiskIOLatency, 3 itérations 128 Mio écrits/lus : même absence de requêtes bloc.
3. Répétition après licence/initialisation Xcode confirmée : même résultat.

Helpers/traceurs bornés et rejoints, scratch supprimé. `iostat` global observe des transferts, mais inclut le traceur et ne permet pas l’attribution au moteur. `ru_inblock/oublock=0` ne prouve pas zéro I/O.

Le moteur utilise des fichiers ordinaires et `preadv`, sans `F_NOCACHE` : le cache fichier macOS peut servir des données en plus des 3 Gio de banques explicites. Sa part propre au modèle n’a pas été mesurée.

**Restent non mesurés :** latence NAND, queue du contrôleur, octets physiques par requête, cache fichier propre au modèle, fraction SSD réellement critique. Aucun conseil d’achat SSD ne découle de ces traces.

## 8. Calage, effet de l’observateur et acquisitions interrompues

Le temps vient de `time-info` et du timebase 125/3, pas du seul start-date du TOC. Une capture initiale avait un décalage TOC/origine réelle. Les lectures donnent un contrôle indépendant du GPU : nombre de retours et octets exacts, syscalls contenus dans leurs jobs natifs parents.

- Courte : correction centrale **+6 666 ns**, demi-largeur compatible **1 292 ns**, 2 619 lectures.
- Première : **−23 624 ns**, demi-largeur **1 396 ns**, 5 244 lectures ; 297 lots à un job confirment l’emboîtement.

Hypothèse : offset constant sur chaque fenêtre. Ce n’est pas une preuve de toutes les horloges système. Un mauvais calage de quelques dizaines de microsecondes affecte les petits spans répétés 48 fois/token.

Effet observateur sur les mêmes indices : **113,755 ms/token tracés contre 91,671 ms au contrôle**, et **103,204 contre 91,993 ms** sur l’autre fenêtre. Cela mélange instrumentation, cache et conditions ; on ne transforme pas le budget instrumenté de 12 ms en gain release garanti.

Échecs conservés : prévols/exports initiaux ; lancement HOLD interrompu après 218,4 Mio de swap entre essais ; captures lourdes interrompues après 104,19 Mio puis 5,44 Mio de Swapout. Pour la première, les snapshots montrent que les 104,19 Mio surviennent **après** la phase `trace_1` validée, sans valider le test complet à 6 phases.

La courte capture a terminé chauffe/contrôle avant/trace_1, validé 128 sorties, 248 320 logits finaux finis et états finaux complets, fermé ses JSON puis arrêté volontairement **notre** processus. Zéro nouveau Swapout sur toute sa fenêtre ; footprint natif aux frontières ≤7,554 Go. Le SIGTERM planifié n’est pas présenté comme un test natif complet passé : `trace_2/trace_3/control_after` non exécutés.

## 9. Plafonds conditionnels et classement issu du profil

Pour passer de **11,5 à 15 tok/s**, il faut enlever **20,29 ms/token**, soit **23,33 % de latence**. Aucun profil ne prouve que cette somme est récupérable.

Les plafonds ci-dessous supposent le reste du travail et les queues comparables. Formule : débit relatif = `T / (T − budget)`. **Ils ne s’additionnent pas et ne sont pas des prédictions de la release.**

| Priorité historique | Piste | Budget / plafond optimiste observé | Risque et lecture |
|---|---|---|---|
| 1 | Réduire primitives, construction et encodage MLX tout en gardant les disponibilités précoces | 11,8–12,1 ms/token CPU actif/GPU idle dans les soumissions ; environ **+12–13 %** dans ces seules fenêtres si entièrement effacé | Surcoût Instruments ; encoder/barrières indispensables ; déplacer les commits peut retarder les routes/Hot. Gain release à mesurer |
| 2 | Cache global et redistribution des slots à 3 Gio | Queue logique exposée 27–31 ms/token ; «lectures gratuites» donnerait environ **+35–38 %** dans les fenêtres | Borne irréalisable telle quelle, pas une politique de cache validée. Le port partagé ARC essayé ensuite est négatif, voir §10 |
| 3 | Cache-map speculation / GDN différé de Sushi | AllHot 12,4–15 % dans les fenêtres fines ; préfixes éligibles 2,37–2,72 ms/token de durée totale, **0,38–0,47 ms seulement de GPU idle** | Le préfixe inclut plus que GDN. PLE présent chez nous ; rollback exact GDN/conv/HC/injection/initialisation. Gain exposé faible face au risque |
| 4 | Accélérer un vrai kernel producteur | 57–63 ms/token de commandes GPU actives | Pas de labels/counters permettant un plafond par kernel ; GPU actif inclut stalls. Choix du kernel à qualifier |
| 5 | Dédupliquer les métadonnées par lot | Au plus environ 0,11–0,12 ms/token de `fstat` | Faible plafond ; garder erreurs troncature/bornes |
| 6 | Accélérer uniquement copie/readback routes | Copie 0,005–0,006 ms/token ; résidu GPU idle 0,08–0,11 ms | Ne retire pas les producteurs ni 38 ms de calcul |

Hétérogénéité de cache : 200 sélections par couche sur 20 tokens, mais 12 à 129 misses selon la couche avec la même capacité 53. Cela justifiait le replay puis un port, **pas** l’affirmation qu’une couche peut céder ses slots sans effet futur. Le head MTP résident est distinct des 3 Gio target.

Le cache de préfixes SSD vise surtout le TTFT/reprise d’un agent ; il ne reçoit pas le plafond de gain du decode natif.

## 11. Correction, tests et limites de preuve

- Les comparaisons exigent valeurs non vides, tailles attendues, finitude et référence indépendante ; les traces naturelles vérifient leurs états finaux et logits finaux complets entre phases et les goldens externes.
- Suite Rust du profilage : **278 passés /167 ignorés** en MLX/chat ; **248 /6** CPU/chat. Les tests physiques sélectionnés séparément ne sont pas remplacés par ces suites.
- Python : 384 tests avant correctif d’horloge, 214 après, puis 101 exports après correction lint ; **230 tests** exports/profilage/supervision passent pour la clôture d’attribution. Ces nombres sont des étapes de vérification, **pas des suites à additionner**.
- Analyse d’intervalles : oracle indépendant par ensembles, **3 375 unions +3 375 intersections** sur grille finie 0..4, 3 bornes invalides, XML valide +5 XML invalides/vides. Mutation max→min détectée, puis version restaurée repasse.
- Kani : contrat CPU des huit compteurs `u64/usize` arbitraires sans hypothèse, 4 couvertures ; domaine borné/contrat concerné uniquement. Autres tentatives : interning arrêté à 4 Gio RSS ; vraie entrée MLX bloquée par ICE ; CBMC ne parse pas le contexte C++ Apple ; CrossHair absent.
- Fmt, Clippy strict, Ruff, compilation Python, analyse des exports, YAML et câblage CI PR/push main contrôlés selon les étapes documentées.
- **Aucune preuve universelle** de Metal, concurrence, allocator ou génération. Pas de run GitHub de l’arbre local non publié ; existence du workflow ≠ CI distante verte.
- Labels d’encodeurs, compteurs shaders et I/O bloc manquants : pas de compte de dispatch exact, d’occupation ALU ou de temps SSD physique inventé.
